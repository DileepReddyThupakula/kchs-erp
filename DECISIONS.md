## 7. Fees (Module: Fees, Part 1, 2026-10-12)

| # | Decision |
|---|---|
| F1 | Monthly due day: **10th**, editable by Admin per plan (per year) and per installment. |
| F2 | **No late fee.** Reserved for later without a rebuild: `fee_heads.late_fee_rule`, `fee_receipt_items.fine_paise`. |
| F3 | Exam: **one-time** plan, amount **₹0 until Admin enters it** per class. Admin can create any custom head with any plan. |
| F4 | Books: **₹0 until Admin enters it** per class, one-time. |
| F5 | Mid-year joiners: **monthly plans charge from the joining month** (the annual amount is split over 12 months and only the remaining months are charged). One-time/custom plans are generated in full, and Admin reduces them with a **fixed concession + reason** (audit-logged). |
| F6 | **Default plans (my default, you didn't answer this one):** Tuition = Monthly, Exam = One-time, Books = One-time. Admin can change the default per class and override per student. |
| F7 | Money is integer **paise** everywhere. Equal monthly split: remainder in the **last** installment. Percentage plans: each share rounded down, remainder in the last. Percent concession: rounded down per installment. Fixed concession: taken from the **last** installment backwards. A concession never exceeds the unpaid part of a due. |
| F8 | Receipt numbers: `<prefix><financial year>/<0001>` (e.g. RCPT-2026-27/0001), per April–March financial year of the receipt date, **gap-free and unique even with simultaneous saves** (tested with 8 parallel connections). Receipts are never deleted; Admin cancels with a reason, dues go back to unpaid, the number stays visible as cancelled. |
| F9 | Payments go to the **oldest due first**, or to the dues chosen (oldest first among them). Paying more than is due is blocked. Only Admin can date a receipt other than today. Non-cash payments need a reference number. The collector is recorded on every receipt. |
| F10 | Dues are generated automatically on enrolment and whenever the fee structure, a student's plan, admission date or class changes. Regeneration never duplicates and never removes or reduces paid dues. On a plan change, unpaid dues of the old plan are voided (kept for history) and the rest of the annual amount moves to the new plan. |
| F11 | Access: Admin everything. **fee_collection** duty: read all fee data, collect, print. No changes to setup, amounts, plans, concessions; no cancelling. **Everyone else: no fee data at all**, even class teachers (RLS + API tests). |
| F12 | Demo: `npm run seed:demo-fees` / `npm run wipe:demo-fees -- --yes` (removes demo receipts, overrides, concessions and the demo "Three terms" plan, resets the receipt counter to the last real receipt). Real fee setup (tuition from `school_reference.json`) is kept. |
| F13 | **Special fees (campaigns):** each one gets its own fee head and its own plan (one-time with a due date, or custom installments by %). Amount: one for all, or per class. Who pays: all active students of the year, chosen classes, chosen sections or chosen students; the member list is stored, so later joiners are added only by Admin. "Apply existing concessions" is a choice at creation (default: no). Regular dues regeneration never touches special-fee dues. |
| F14 | Editing a special fee (amount / class amounts / one-time due date) changes **unpaid dues only**; part-paid and paid dues keep their amount and date. Cancelling voids unpaid dues only; paid dues and receipts stay; the head is deactivated. Only Admin, through functions (no direct writes); all audit-logged. |
| F15 | **Miscellaneous receipt** (Admin): any active fee head except a special-fee head, optional student or a payer name, same gap-free number series (tested with simultaneous saves), `kind = misc`, no due. Cancelled like any receipt. |
| F16 | **Fee screens (Part 2).** Fee setup (Admin) has four tabs: Amounts per class, Fee heads, Plans & schedules (per-installment due dates; custom plans by %), Special fees. Changes update unpaid dues only. "Recalculate dues" rebuilds a year safely. Concessions (Admin) per student, one head or all, with a reason. |

## EX (Exams & marks, Module 6: database part)
Answers given: custom editable scheme; Nursery to UKG grades and remarks; co-scholastic grade A to E per term; D4 report card; remark bank + typed Telugu; AB counts as 0, N/A left out; strict lock; term dates editable; per-subject maximum override.
- **EX1 The scheme is data, not code** (per academic year and class, Admin only): *exam components* (FA1, SA1 or any name, with a maximum, reorderable), *result groups* (a term, the final, or a part) that combine components or other groups by **sum, average or best-of-N**, optionally **scaled** to a maximum (a member can be scaled too). "Apply the starting scheme" creates the placeholder below; everything can then be edited. **VERIFY with the school:** FA1-FA4 each out of 20 and SA1, SA2 each out of 80; *Term 1 FA* = average of FA1 and FA2 scaled to 20; *Term 1* = Term 1 FA + SA1 = 100; *Term 2* likewise; *Final* = Term 1 + Term 2 = 200.
- **EX2 Calculation is done by the database** whenever a mark, the scheme, a pass mark or the grading scale changes: subject total, group total, percentage, grade, grade point and pass/fail are stored in `subject_results` and the student's overall result in `student_results`. Nobody types a total or a grade. The steps of every calculation are stored (`calc`) so a screen can show them. Overall result of a term: **Pass only if every marks subject passes**; **Incomplete** while any exam of a subject has no entry (never shown as Fail); Fail otherwise. Grade point of a student = average of subject grade points.
- **EX3 Absent and Not applicable:** *Absent* scores 0 towards the total, is shown AB and stores no number (never a typed zero). *Not applicable* removes that exam for that student and subject: its marks AND its maximum leave the total, so the percentage stays fair. A mark not yet entered is "missing": counted as 0 with the maximum kept, and the result is flagged incomplete. Marks may have one decimal. Scaled values are rounded to 2 decimals; pass/fail uses the percentage at 4 decimals, not the rounded one shown.
- **EX4 Pass marks:** default 35% (School settings value `default_pass_percent`), editable per subject and class (Hindi separately). **Maximum:** one per exam component and class; Admin can override it for one subject (e.g. Drawing out of 50).
- **EX5 Grading scale** (V1, **VERIFY**): A1 91-100 (10), A2 81-90 (9), B1 71-80 (8), B2 61-70 (7), C1 51-60 (6), C2 41-50 (5), D 35-40 (4), E 0-34 (fail). Admin only; a grade is found from the highest band whose start is not above the percentage, and the lowest band must start at 0.
- **EX6 Class modes:** each class is *marks*, *grades* or *remarks*. Default: Nursery, LKG and UKG = grades, the rest = marks. In a grades class every subject gets a grade A-E (per term) and an optional remark; in a marks class only the co-scholastic subjects (Art, Work & Computer, Physical & Health, Value Education) get a grade per term; the grade list A-E is editable and never added into the marks.
- **EX7 Who can do what (R18):** Admin only: scheme, groups, pass marks, grading scale, class mode, remark bank, lock and unlock. A teacher reads only the marks and results of their own (section, subject); the class teacher gets no extra marks access. Totals across subjects (`student_results`) are readable by Admin and the duty only. Writes go only through checked functions.
- **EX8 Strict lock:** Admin locks a result group (its exams and everything built from them) or one exam. A locked exam cannot change by any route, **not even by Admin**, until Admin unlocks it with a written reason (audit-logged). Unlocking an exam unlocks the results built from it. Locked results are a snapshot: a later grading-scale change does not rewrite them. The scheme of a class cannot change while a part of it is locked. This replaces the older "Admin may edit after lock".
- **EX9 Remarks and Telugu:** the class teacher writes the term remark from an editable **remark bank** (English + Telugu, Telugu **VERIFY with a Telugu speaker**) or types their own English and Telugu. **Student remarks are never machine-translated**, so nothing about a student leaves the school's server (this keeps the earlier privacy rule).
- **EX10 Report cards:** `report_card_data` is the only way to read a whole card; allowed for Admin, the `all_class_marks` duty and the **class teacher of that student's section** (the one exception to "only subjects you teach", because a card shows every subject). ## PF — Performance findings (production build, 439 demo students, 2026-10-17)
- **PF1 How it is measured:** `npx next build`, `KCHS_TRACE=1 npx next start -p 3200`, then `node --env-file=.env.local scripts/perf-measure.mjs http://localhost:3200 both` (prints, per page: hard-load min / median ms, HTML size, database calls and their time). Never judge speed on `next dev`. `npm run seed:demo-bulk` tops the demo school up to the real strength (439); `npm run wipe:demo-bulk -- --yes` removes only those.
- **PF2 What costs time:** every database call from the app costs about 55 to 70 ms (a network round trip), so the number of calls ONE AFTER ANOTHER matters far more than how much work the database does. Calls made at the same moment overlap; calls that wait for each other add up. The fixes are: fewer calls, more of them at once, and one function that does the work of many.
- **PF3 Admin dashboard = ONE function.** `public.admin_dashboard(year, today)` (Admin only) returns the counts, unmarked attendance, leave waiting, current notices with read counts, translation usage, exam reminder and the diary board in one call. Dashboard before → after: **20 → 5 database calls** (4 are the sign-in and settings every page makes; 1 is the function), **741 / 964 ms → 230 / 282 ms** (fastest / median hard load). Teachers keep their own queries (their numbers depend on their own sections).
- **PF4 Students list = pages, in the database.** `public.students_page(...)` does search (name, admission no, parent name or phone, case-insensitive, `%` and `_` taken literally), the class / section / status / documents / government-field / not-enrolled filters, sorting (name, admission no, class, date of birth, status) and paging, and runs as the signed-in person, so the row-level rules apply unchanged (a teacher only ever gets their own sections' students and never the government fields, masked IDs or document gaps; their document / government filters are ignored). The list sends 25 students at a time (25 / 50 / 100 / 250), the state is in the URL (`?q=&class=&section=&status=&docs=&gov=&enrol=&sort=&dir=&page=&size=`), and Export fetches every student that matches the filters, or the selected ones, only when asked. Students before → after: **18 → 8 calls, 847 KB → 219 KB of page, 939 / 1138 ms → 215 / 316 ms**. The list leaves out the heavy government fields; they come only with an export.
- **PF5 VACUUM / ANALYZE after a big load.** Right after a bulk insert (seed scripts, an Excel import, a migration that moves many rows) the database has no fresh statistics, and the planner picked slow plans (a teacher's results read took 509 ms instead of under 40 ms). Run `VACUUM (ANALYZE)` on the affected tables after any bulk load (Supabase also does it by itself, but not instantly). Do this once after the real student import.
- **PF6 Hosting region.** The Supabase project is in Mumbai (`ap-south-1`). When the app is deployed, run the server functions in the SAME region (for example Vercel `bom1`); an app server in another continent would add 150 to 250 ms to EVERY database call and undo the work above. The numbers here are from a laptop talking to Mumbai (about 55 ms a call); a server in Mumbai should be faster. Keep the school's real data in Mumbai too.
- **PF7 What was still slower (done in PF8):** Fees → Collect (27 calls) and Exams → Marks / Results (about 20) were the slowest pages; PF8 brought them to one function each. Still open: the Government export page reads all students at once (Admin only, rare), and the shared sign-in check (staff + duties + settings + years, 4 calls on every page) could become one function.

## SEC — A deactivated or removed person gets nothing (2026-10-17)
- **SEC1 Rule:** a sign-in token only proves who someone is; what they may see is decided by the database on EVERY query. A person who is deactivated (inactive / left), has their role removed, is unlinked from their login, has their staff record deleted, or whose login is deleted gets no rows, no functions, no files and no pages, even while their old token is still valid. Proven by `tests/db/20_deactivated_staff.sql` (33 checks), `tests/api/deactivated-staff.mjs` (every table, function, write and file bucket, with an Admin and a teacher who has every duty, for six ways of losing access, using the SAME old token) and `tests/api/deactivated-staff-pages.mjs` (18 pages redirect to the sign-in page with the old cookie; run it with `TEST_APP_URL=http://localhost:3200`).
- **SEC2 Fixed on the way:** a deactivated person could still read their OWN staff row. It is now readable only while they are active and have a role (`staff_select`).
- **SEC3 Token lifetime:** the access token lasts **1 hour** (3600 s, the Supabase default; seen in tests). It can be shortened in the Supabase dashboard (Auth settings, "JWT expiry"; Supabase advises 5 minutes to 1 hour; we cannot change it from here); we recommend leaving it, because the database already refuses a deactivated person immediately. Saving a staff member as inactive / left, or removing their role, now also bans their login so no NEW token can be issued; re-activating lifts the ban.

## FA — Fee access: Admin and chosen office staff only, never a teacher (2026-10-29)
- **FA1 Rule (your instruction):** fee pages, fee reports (collection, dues, receipts, concessions, special fees), the payment settings and the UPI QR file are for the **Admin** and for **office staff the Admin picks one by one**. A teacher can never have fee access, whatever other duties they hold. The Admin can remove an office person's fee access at any time and it stops **immediately** (the check is live on every query).

## CE — Certificates (TC, bonafide, study): questions being answered one at a time (started 2026-10-30; not built yet)
- **CE1 TC layout (decided 2026-10-30):** the TC layout is ONE adjustable template, started from the commonly used AP fields (admission number, name, parents, nationality, religion, caste, date of birth in figures and words, class studied, last exam result, conduct, fees paid, reason for leaving, date of leaving, date of issue, remarks), in English and Telugu text; caste and religion are optional on the print (the school confirms what must appear). The owner brings a real TC to compare and the template is then matched to it. Until the owner confirms the layout, EVERY TC print shows a clear "DRAFT layout - not for issue" watermark on screen and on paper, and issuing a real TC (the one that sets the student to Left and uses a number) is BLOCKED while the draft layout is active. The owner switches the draft flag off once the layout matches.
- **CE2 Who issues (decided 2026-10-30):** the TC: Admin only. Bonafide and study certificates: the Admin and an OFFICE person who holds the "Certificates and ID cards" duty. A teacher can never issue any certificate, even if given that duty (enforced in the database by role, not only by duty). Every issue and reprint is audit-logged.
- **CE3 Numbering (decided 2026-10-30):** a separate gap-free series per certificate type (TC, bonafide, study) and per academic year, e.g. TC/2026-27/001. (1) The prefix and the starting number of each series are Admin settings; before the first certificate of a series in a year, the Admin can set its starting number (so the first TC can continue the school's existing register). (2) The starting number can be changed only while no certificate of that series exists for that year; every change is audit-logged. (3) A number is given only at the moment of issue, never before, never skipped, never reused; a cancelled certificate keeps its number and shows as Cancelled with the reason. (4) Two people issuing at once never get the same number (concurrency test, like the fee receipts). (5) A certificate register page per type and year (number, student, date, issued by, status) for the Admin: printable A4 and exportable, the export logged.
- **CE4 Checks before a TC (decided 2026-10-30):** a checklist, shown to the Admin only (the TC is Admin only), each item green / amber / red with a link to fix it: (1) dues cleared (shows the amount and a link to Collect fee), (2) the student is in a class and the year's results are recorded (amber warning, not a block, if the year is unfinished), (3) required details complete (name, parents, date of birth, admission number, class). "Issue anyway" needs a tick and a written reason, saved on the TC record and in the audit log; only the Admin can use it. The check runs in the database at the moment of issue, so it cannot be skipped by calling the function directly. An office person who issues bonafide / study certificates never sees any fee amount or dues check (those have none). Tests: TC with dues refused without the override, accepted with override + reason, missing reason refused, non-Admin refused in every case.
